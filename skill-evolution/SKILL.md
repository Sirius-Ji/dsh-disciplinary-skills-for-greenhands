# SKILL：半自动技能进化

**适用场景**：出现值得沉淀的重复经验；或用户纠正了我；或我刚完成一次重大事故修复。

**不适用**：一次性的偶发问题；用户没纠正、也没复发迹象的个人偏好。

**一句话原则**：**提议权自动，写盘权人工。** 我可以随时提议，但不许自己动手。

## 一、触发条件（五选一，必须附证据锚）

| 条件 | 可接受的证据锚 |
|---|---|
| 同一坑踩 ≥3 次 | ARCHIVE.md 里 ≥3 条同症状/同锚点的记录 ID |
| 重大事故修复 | 本次修复的前后对比（改前必红、改后必绿） |
| 重复动作 ≥3 次 | 本会话内的重复工具调用序列 |
| 通用工作流被长期复用 | ≥2 个不同项目/工作区在用 |
| 用户明确纠正 | 用户原话引用 |

**没有证据锚 ⇒ 不许提议。** 凭"感觉这个坑好像踩过"不算。

## 二、判定：改旧还是新建（5 轴 rubric）

| 轴 | 权重 | 命中标准 |
|---|---|---|
| 同触发症状 | 20% | 相同的报错类 / 相同的前置条件 |
| 同根因层 | 20% | 同属一个病根谱系（见 recurring-root-cause-atlas） |
| 同修法 | 20% | 规则条目可合并而不冲突 |
| 同操作步骤 | 20% | 复用 ≥60% 的命令/流程 |
| 同适用范围 | 20% | 适用场景重叠 ≥60% |

**≥3 轴命中（=60%）⇒ 改现有 skill；否则新建。**

这是**打勾判定，不是数值估算**——模型算不出真正的相似度，别假装能算。

新建时必须在草案里额外回答一句：**为什么不能并入现有能力簇？**

## 三、草案格式（只在对话里出现）

固定三段，缺一段不算草案：

1. **触发证据** —— 锚点 ID / 本次前后对比 / 用户原话；
2. **改动 diff** —— 改哪个文件、加哪几行、删哪几行（新建则给全文）；
3. **风险与回滚** —— 最坏影响是什么、怎么退（`git revert <sha>`）。

草案只在对话里打印。**在用户给出明确的"准入 / 写入 / 批准"之前，一个字节都不许写盘。**

## 四、准入后的写入流程（严格按序 · **派生先行**）

> **为什么是「派生 → 核验 → 提交」，而不是「提交 → 派生」？**
> 因为 `.hooks/verify_3ends.py` 已挂进 pre-commit：**提交那一刻**它会比对三端哈希，
> 不一致就直接阻断。所以必须先把改动派生出去、让三端对齐，提交才通得过。
> 反过来做（先 commit）会被自己的门禁拦下 —— 那不是钩子坏了，是顺序错了。

### 4.0 高危变更：先出《全链路影响面清单》，再动手

涉及**核心结构文件**（`AGENTS.md` / `AGENTS.repo.md`、SKILL 模板、目录搬迁）的路径或文件名变更，落盘前**必须先产出影响面清单并经人过目**，逐项点名：

1. **派生脚本** —— 有没有写死源文件名？
2. **pre-commit 钩子及其调用的门禁** —— 文件名常量被用在几处？（常见陷阱：一个常量同时管"暂存名匹配 / git cat-file 路径 / 生效端路径"三件事）
3. **三端哈希比对逻辑** —— 仓库内名与生效端名是否已经分离？
4. **Git 提交触发条件** —— 改名后"暂存区是否含该文件"的判定还成不成立？
5. **文档/注释里写死的路径** —— 会不会把后人带沟里？

⚠️ 改名还会**改变派生的语义**：从「同名复制」变成「**改名**复制」（仓库内 `AGENTS.repo.md` → 生效端 `AGENTS.md`）。

### 4.1 两类改动的路线不同

**A. 纪律改动（端② `skills/AGENTS.repo.md`）—— 必须派生先行**

> ⚠️ 仓库内名与生效端名**刻意不同名**：仓库 `AGENTS.repo.md` / 生效端 `AGENTS.md`。
> 因为端② 嵌套在 `~/.dsh` 下，若仓库里仍叫 `AGENTS.md`，宿主会把同一份纪律既当
> "工作区指令"、又当 "skills 子目录附加指令"各注入一次（实测成对 seq=1862/1874、
> 2495/2518），既浪费上下文，又让运行态验证器可能拿嵌套文件顶替根文件判定 ⇒ 假绿。

1. 查工作树：`git status --porcelain` 必须为空；脏就先 commit 或停下报告；
2. 改端② `skills/AGENTS.repo.md`；
3. **派生**（⚠️ 是**改名**复制，不是同名复制）：字节级复制到 端① `~/.dsh/AGENTS.md` **和** 端③ `<你的模板库路径>\skills\AGENTS.repo.md`。
   此时端③ 处于「临时脏」状态 —— 这是预期，不要慌；
4. **核验**：`python .hooks/verify_3ends.py --all` 必须输出 `✓ 三端一致，行尾干净`；
5. **提交**：`git commit`（消息带证据锚，如 `refs H-0042`）；
6. **推送**：`git push origin master`，并确认裸库 `refs/heads/master` 已更新；
7. **端③ 收尾**：`git fetch origin && git reset --hard origin/master`（清掉第 3 步的临时脏状态，对齐新提交）；
8. 报告：改了哪一端、哪几行、哈希前后值、回滚命令。

**B. 技能改动（端② `<name>/SKILL.md`）—— 钩子不管技能**

1. 查工作树干净；
2. 改端② 的 SKILL.md；
3. **直接 commit**（暂存区不含根 AGENTS.md ⇒ 钩子只提示、不阻断）；
4. 推送；
5. **端③ 的派生由快进完成**：`git fetch origin && git reset --hard origin/master`；
   ⚠️ **不要**在 commit 前手工把 SKILL.md 拷进端③ —— 那会让端③ 变脏，之后的快进会失败；
6. 核验端②/端③ 的 SKILL.md SHA-256 一致；
7. 报告。

### 4.2 派生失败怎么办（逃生门）

派生到端① 可能因**文件被占用 / 权限不足 / 沙箱拒绝**等非内容性故障失败。此时：

1. **先重试一次**，并保留完整错误原文（不要只说"失败了"）；
2. 仍失败 ⇒ 允许 `git commit --no-verify` 先把端② 的成果入库，**防止修改成果丢失**；
3. **但必须在回复里明确写出下面四项，缺一不可**：
   - ⚠️ 原话写明 **「本次用了逃生门（--no-verify）」** —— 不许含糊说"已提交"；
   - **原因**：贴出派生失败的错误原文；
   - **遗留待办**：哪一端还没派生（通常是端①，可能还有端③）；
   - **补救命令**：下次开工第一件事要跑什么。
4. 逃生门只保证「成果不丢」，**不改变「三端最终必须一致」的目标**。
   在补齐派生并核验通过之前，这件事视为**未完成**。

### 4.3 报告格式（必须能自证）

```
端② : <sha16>  <字节数>  CRLF=<n> 裸LF=<n>
端① : <sha16>  <字节数>  CRLF=<n> 裸LF=<n>
端③ : <sha16>  <字节数>  CRLF=<n> 裸LF=<n>
核验 : verify_3ends.py -> ✓ / ✗（✗ 必须附原因）
提交 : <sha> <消息>
遗留 : 无 / 逃生门原因 + 待办
```
### 4.4 门禁与工具自身的三个假绿（真实踩过）

| 陷阱 | 现象 | 已固化对策 |
|---|---|---|
| **cwd 不在仓库** | 手动跑 `verify_3ends.py --all`，cwd 是 `~/.dsh` 而不是仓库 ⇒ 打印「不在 git 仓库内，跳过」并 **exit 0** | `--all` 前提下视为**判定失败 exit 1**；新增 `--repo <路径>` 显式指定仓库根；负向测试必须为红 |
| **中文/符号乱码** | Windows 控制台默认 GBK：中文输出变乱码，容易被当成"正常输出"糊过去；更狠的是 `print("✓")` 直接抛 `UnicodeEncodeError` —— **操作其实已经成功，却以 exit 1 收场（假红）** | 脚本内 `sys.stdout.reconfigure(encoding="utf-8")` 钉死；或输出只用 ASCII 记号 |
| **编译缓存污染** | `python -m py_compile` 生成 `.hooks/__pycache__/`，被 `git add -A` 带进提交 | 语法检查改用 `compile()` 不落盘；提交前 `git status` 不许有 `??` |

判据：**"这个绿能证明被测对象真的跑了吗？"答不上来，就不算数。**

## 五、纪律晋升（从技能到宪法）

如果提炼出的经验**跨项目成立**（不依赖某个项目的目录结构/命令/约定），它就是纪律：

- 提议写进 `AGENTS.md` 的对应章节，格式固定：**一句话可执行规则 + `(详见 skill: xxx)`**；
- 纪律区只放纪律。**技能索引、目录、清单、说明性文字一律不得进 AGENTS.md**；
- 同样需要用户"准入"才能落盘，且必须走第四节的派生流程。

## 六、回滚

- 单次改动 ⇒ `git revert <sha>`（保留历史，不 force push）；
- 派生出错 ⇒ 从端② 重新复制覆盖端①/端③，再核哈希；
- 端① 改坏且未提交 ⇒ 用 `.backup/AGENTS.md` 还原（这是端① 唯一的版本保护）。

## 七、硬性禁止项（违反即事故）

- ❌ **未经"准入"就把草案写盘**——这是本机制的第一红线；
- ❌ 直接编辑端① `~/.dsh/AGENTS.md`——它没有版本控制，必须由端② 派生；
- ❌ 同时改三端——只改端②，再派生、再核哈希；
- ❌ **往 `AGENTS.md` 添加任何非纪律内容**（技能索引/目录/清单）——2026-11-02 已被用户明确否决过一次；
- ❌ 工作树脏时改文件；
- ❌ 把"我提议了"说成"我已记录"；
- ❌ 用模糊的相似度估算代替 5 轴 rubric 打勾；
- ❌ 在没跑过触发证据的情况下声称"这是第 3 次"。
- ❌ **先 commit 后派生**（会被自己的 pre-commit 拦下；正确顺序是派生 → 核验 → 提交）；
- ❌ **用了 `--no-verify` 逃生门却不报告**（必须原话写明「本次用了逃生门」+ 原因 + 遗留待办）；
- ❌ 在 commit 前手工把技能文件拷进端③（会让端③ 变脏，导致之后的快进失败）。
- ❌ 把"前提缺失"跑出来的 exit 0 当成通过（门禁自己也要自证前提，见 4.4）；
- ❌ 让 `py_compile` 产物（`.hooks/__pycache__/`）混进提交。
