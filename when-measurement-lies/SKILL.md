# SKILL：测量工具会骗人

> ⚠️ 使用前提：**如实报告失败**（见 `你项目的**状态文档** 项目规范 §诚实报告失误）。

**适用症状**

- 报告的数字 / 结论**与预期不符**，但**代码看起来是对的**（反复读代码找不出毛病）
- 反复改代码却"**怎么改都一样**"——量出来的数字纹丝不动
- **断言 / 自检永远通过**（改坏了也绿），或者**永远失败**（修好了还红）
- 同一件事**两种工具量出不同数字**（谁对？）
- 修完"数字变好了"，但**用户看到的现象没变**（或反过来）

**不适用**

- 测量工具本身就是被测对象（那时候要测的是它的契约，不是它给出的数）
- 现象**稳定复现且代码明显错**（直接读代码更快，不必先怀疑测量）

---

## 快速判断（30 秒）

```
1. 你量的那个数，是"你以为的那个东西"吗？
       → 换一种口径再量一次（换工具 / 换层 / 换坐标系）
2. 两种口径的数不一样 → 先别下结论，把差异定位到"读数的那一步"
3. 你的断言，在"把修复去掉"之后还会绿吗？
       → 会绿 ⇒ 断言没有灵敏度，它没在测任何东西
```

**判据一句话**：**数字不对时先怀疑尺子**。改代码是成本最高的一种反应。

## 核心原则

### 原则 1：结论与预期不符 ⇒ 先验证测量本身

顺序永远是：**测量可信吗 → 口径一致吗 → 再看代码**。反过来做（先改代码）会让你在错误的战场上改很多轮，
且每一轮"看起来都有道理"（因为数字确实在动，只是动的是别的东西）。

### 原则 2：先确认"你量的东西就是你改的东西"（作用层）

最隐蔽的一类：**探针挂在错误的层**上，于是它量的永远不是你要改的那部分。
在这种状态下，**"放宽/收紧判据"永远无效**——因为你改的那个条件根本没被求值。

### 原则 3：量测区域必须与标注区**物理分离**

量像素/墨迹/包围盒时，任何**为了给人看而画上去的东西**（标签、参考线、水印、图例）
都会进入测量区，产出**看起来很像真的**假数字。

### 原则 4：断言必须在"修复前"能红（灵敏度自证）

一条断言如果在**修复前也是绿的**，它就没有测试任何东西。
**断言的价值 = 它在坏状态下变红的能力**，不是它在好状态下变绿。

### 原则 5：异步 / 缓存 / 渲染的"完成"不是"落盘"（时间层）

- 任务"跑完" ≠ 结果"写盘完"
- 渲染"调过了" ≠ 布局"算完了" / 缓存"生效了"
- 长任务结束后去读产物，可能读到**半成品**（数字偏小、图不全）
⇒ 取证要么**等落盘**（按 mtime 确认最后一批文件），要么**在同一次运行里串行取**。

### 原则 6：集合类判定（"可达 / 有效 / 在用"）必须用**严格口径**

判"某个文件 / 分支 / 缓存条目**还有没有用**"时，**"可达"只能按"当前代码真能产生的组合"定义** ——
不能把**历史默认值**、**曾经传过的参数**也算进"可达"。

**本项目实测（2026-10-06，清理公式缓存）**：
- **宽口径**（把历史默认 `wrap=493.0` / `465.74` / `None` 也算"可达"）⇒ 把 **801 个 `wrap=493.0`
  的旧键副本误判为"活"** ⇒ 只敢删 1160 个 ⇒ **清理不彻底**；
- **严格口径**（只认 `colour ∈ {FFA8CC,111111,FF0000,0000FF}` × `display ∈ {0,1}` ×
  `wrap ∈ {_wrap_width_for(meta.font), inf}`，即**当前源码里真会传出去的组合**）⇒
  **死 2005 / 活 671**。

**为什么"宽口径"更危险**：它**不报错**，只是**悄悄多保护了一批死物** ——
你会以为"我已经盘过了"，其实盘的是**另一套参数**。（与原则 2 的"作用层"同源：
**你以为你在数的集合，不是真正在用的集合**。）

**判据**：写下"可达"的定义时，**逐项对着当前源码的调用点**核，不要凭印象加历史值；
**每加一个历史值，都要问"现在还有谁传它"**（本项目答案：没有 ⇒ 不该算可达）。

（对应下节 §六层分类 的 **⑥ 集合层**；它与 ② 作用层的区别：
作用层是"判据**没被求值**"，集合层是"判据**被求值了、但口径太宽**" ⇒ 修法不通用。）

## 上手核对清单（第一次怀疑测量时逐条过）

```
□ 1  这条数字是"哪个进程/哪次运行"产生的？（长任务：等落盘了吗）
□ 2  读它的工具，编码是否显式？（shell 默认可能是 GBK）

□ 4  它的测区里，有没有"为了给人看"而画上去的东西？
□ 5  同一个量，换一种工具/口径再量一次，两个数一样吗？
□ 6  我这条断言，把修复去掉之后还会绿吗？
□ 7  探针自己有没有失败？（stdout 之外，stderr / 退出码 / 日志看了吗）
```

**七条里任一条答不上来，就先别下结论**——把"答不上来的那一条"当成待办的侦察任务。

## 过滤 = 新测量：给输出加"形状假设"，过滤本身就变成会骗人的尺子

**核心口径**：**过滤不是"读取"，是"新的测量"**。
你写下的每一条过滤条件，都是给输出加了一个**形状假设**（"标题长这样"、"失败长这样"、"这段应该含某个词"）。
**假设一旦错，你量到的就不是真相，而是"你以为的形状"** —— 而且**它不会报错**，
只会安静地少给你几行，让你得出"少了 / 没跑 / 不存在"的结论。

### 判据（统计输出前先问这一句）

> **"我的过滤模式给输出加了什么形状假设？这个假设本身有没有验证过？"**

三条配套铁律：
1. **过滤是"提问"，不是"取证"** —— 可以用过滤来**定位**，但**结论必须回到完整输出上验证**；
2. **"没看到 X" ≠ "X 不存在"** —— 在过滤结果里找不到，只说明"当前条件下没显示"；
3. **要断言"某段没跑 / 某分支没走"，必须用"该段是否输出过标题 / 日志"来证明**，
   而不是"我没在过滤结果里看到它"。

### 本项目两个实例（同一个坑，隔一轮踩两次）

```python
repr('== 气泡公式实时渲染冒烟（某次改动）==')
# startswith('== ') = True
# endswith(' ==')  = False     ← ★ 一个空格之差
```
**⇒ 是我方比对方法错，不是代码问题。** 且这是**同一个坑第二次踩**（离实例 1 只隔一轮）。

### 反模式

- ❌ **用一个未经校验的过滤条件统计输出，然后据此下结论**；
- ❌ **把"过滤后为空"当成"不存在"**；
- ❌ **正则 / 关键词 / 字段切分里隐含的格式假设，从不写出来、也从不验证**；
- ❌ **只在过滤结果里找"能支持我假设的行"**（这已经是"先有结论再找证据"）。

**一句话**：**过滤让你看得更快，但也会让你更确信地看错** ——
下一次统计输出前，先把你的过滤条件当"被测对象"验一遍。

## 加探针会改变时序 —— 观测动作本身会改变被观测现象

**"装个探针看看"不是中性的**：探针会占时间、改 I/O、改调度顺序
⇒ **被观测的偶发现象可能因此变形、变少、甚至消失**。

| 条件 | 耗时 | stderr 行数 |
| --- | --- | --- |
| **探针开**（`qInstallMessageHandler` 接管 Qt 消息） | **53s** | **0** |
| 探针关 | **66.3s** | **123** |

**⇒ 两个后果，都必须记住**：
1. **速度差 20%**：探针**吃掉**了 123 行 stderr 写入（大输出重定向到文件很慢）
   ⇒ 不是"探针变快了"，而是**被观测系统的 I/O 形态变了**；
2. **现场形态变了**：探针关时靠 `stderr` 找线索；**探针开后那些线索只进日志**，
   `stderr` 变干净 ⇒ 拿两次的 stderr 对比会得出**错误的"变好了"**。

**判据**：
1. **探针只许"记录"，不许"接管"**（若必须接管默认输出，要在报告里写明）；
2. **同一现象在"探针开 / 关"两种条件下各测一次**，把两次的**耗时与输出形态**都记下来；
3. 报告里的数字必须标注**它是哪种条件下测的** —— 否则前后两次不可比；
4. 尤其对**偶发 / 时序类**问题：**探针开久了抓不到，可能就是探针自己把它压住了**。

**同族**：本 skill 的"时间层"（异步/缓存的"完成"不是"落盘"）—— 本条是它的**主动版**：
**不是"没等够"，而是"我一等，它就不发生了"**。

## 写/读两侧：PowerShell 重定向默认 UTF-16LE（写侧就出错，读侧才发现）

**本项目第六次踩同一个坑**（AI-1 / AI-1.5 / AJ-3c / 2026-10-21 连踩 3 次）：用 PowerShell 的 `>` / `*>` 重定向
抓程序输出，**默认写 UTF-16LE**（带 BOM `ff fe`）；**按 UTF-8 读会得到空或乱码，且不报错**。

> **版本相关**：本机是 Windows PowerShell **5.1**（默认 UTF-16LE）；**PowerShell 7 默认 UTF-8 无 BOM**
> ⇒ 换到 PS7 上复现不出来，**不代表规则过期**，只代表你没在 5.1 上。

> **硬规则（动手前就该生效）**：要字节就别走 shell 重定向 —— 见 skill `agent-execution-hygiene` 规则 8
> （还有 `read_text()` 归一 CRLF、`Get-Content` 走 GBK、`cmd /c` 吃 `^` 三种同族坑）。

**凶案现场（AJ-3c）**：
```
按 utf-8 读 g_default_out.txt    ⇒ [OK]=0   · stderr 165 行 · QBasicTimer 0 次
按 utf-16-le 读（探测 BOM 之后）  ⇒ [OK]=378 · stderr  81 行 · QBasicTimer 2 次  ← 差之毫厘
```
**⇒ 因为读错编码，我差点把"第二个 ① 现场"当成空文件跳过。**

**判据（照抄）**：
```python
raw = p.read_bytes()
enc, skip = ("utf-16-le", 2) if raw.startswith(b"\xff\xfe") else ("utf-8", 0)
text = raw[skip:].decode(enc, errors="replace")
```
或者**从源头避免**：**别用 shell 重定向** —— 在 Python 里
`subprocess.run(..., text=True, encoding="utf-8")` 拿到字符串再自己
`write_text(..., encoding="utf-8")`（本项目的采样脚本一直这么做；
只有"随手一条 PowerShell 命令"才会踩）。

**为什么反复踩**：`read` 工具读 UTF-16 文件会报 "invalid UTF-8"（**会提醒你**），
但**用脚本按假设编码读不会报错**（`errors="replace"` 还会把乱码变成 `�` 悄悄混进去）
⇒ **越是"自己写的读取代码"，越要显式探编码**。

## 文件复用 ≠ 单次运行 —— 别把"日志文件"当"一次跑"

**同一个日志文件会被多次运行反复写入**（轮转 / 截断 / 追加）⇒
**对着整个文件做统计，得到的不是"某一次运行"的数字**。

**判据**：
1. **"一次运行的结果"只能来自该次运行自己的产物**
   （本项目的约定：`data/tmp/aj*_runNN_stdout.txt` / `_stderr.txt` / 对应的 `qtmsg_*.log`）；
2. **共享日志（`agent.log`）只用来"找人"（时间戳、线程名），不用来"计数"**；
3. 若必须在共享日志上统计，**先按"本次运行的起止时间"切片**，
   并**在报告里声明切片依据**；
4. 尤其当结论是"某功能没生效 / 探针没工作"时：**先排除"我读到的是旧记录"**。

**同族**：本 skill 的"集合层"（**我以为我测的集合 ≠ 我实际测的集合**）——
本条是它在**时间维度**上的版本：**我以为的"一次" ≠ 文件里的"一次"**。

## 截断的 dump 不能反推缺失的标签 —— faulthandler 的 `Current thread`

**faulthandler 的 dump 里，标签本身就是证据**：
- **故障线程**被标 **`Current thread 0x…`**；
- **其它 Python 线程**（含 Qt 建的线程，只要那一刻在跑 Python）标 **`Thread 0x…`**；
- 打印顺序 = **解释器线程列表顺序** ⇒ **故障线程不一定排在第一个**。

## 反模式

### ❌ 只看"过滤后的输出"就下结论（看哪部分的选择错）

**不是工具错，是"我看哪一部分"的选择错** —— 过滤输出 = **主动丢弃信息**，
而丢掉的往往正是**反驳你结论的那一行**。

```
[OK] 动画：进入 AWAKE 播放主坐姿 GIF（idle/default.gif，QMovie 在跑）
[OK] 动画：主坐姿 GIF 在 6 秒内解码完（帧数 564）      ← ★ 决定性线索
```

**⇒ 段根本没被跳过；相反，"帧数 564"（= 真值）才是解释全局的关键**（首次运行完整解码、
后续运行只到 37~52 帧）。**我因为滤掉了 `[OK]`，把最强证据亲手删掉了。**

**判据（照抄）**：
1. **下结论前必须看"完整输出"**；确实需要过滤时，
   **先确认过滤条件不会丢掉"能反驳你假设的行"**（尤其是 `[OK]` / 成功路径的行）；
2. **过滤是"提问"，不是"取证"** —— 过滤可以用来**定位**，但**结论必须回到完整输出上验证**；
3. **"没看到 X" ≠ "X 不存在"**：在过滤输出里找不到的东西，
   只能说明"当前过滤条件下没显示"，**不能**推论"没发生"；
4. 若结论是"某段没跑 / 某分支没走"，**必须用"该段是否输出过标题/日志"来证明**，
   而不是"我没在过滤结果里看到它"。

**同族**：本 skill 的六层分类（工具 / 作用层 / 物理分离 / 时序 / 严格口径）——
本条属于**"看哪部分"的选择错**，是**新的一层**：**观测范围（scope）层**。

中文 Windows 上 shell 默认按 GBK 解码，UTF-8 无 BOM 文件会被拆坏：**行数偏少、字被吃掉，且不报错**。

### ❌ 在错误的层验证逻辑

### ❌ 量测区与标注区重叠

为了给人看而画上去的东西，会成为下一次测量的"数据"。**标注一律离开测区**。

### ❌ 写"永远为真"的断言当通过

绿 ≠ 有效。**每条新断言都要回答"它在什么情况下会红"**；答不上来就补一个能红的。

### ❌ 用一个数字下结论

单点数字可能来自错的层 / 错的区域 / 错的时间。**至少两种口径交叉**，差异要能解释。

### ❌ 按标签分类删东西（"看起来是旧的" ≠ "真的没用"）

删除类操作里，**绝不能按字段值 / mtime / 大小**批量判死 ——

## 边界

### 能识别

- **数字口径不一致**（换工具即暴露）
- **作用层错**（判据改了没效果 ⇒ 先怀疑层）
- **量测区污染**（测区裁干净即暴露）
- **断言无灵敏度**（修复前去跑一次即暴露）
- **时间层错位**（同一次运行内串行即排除）

### 不能识别

- 工具**完全不可用**（比如日志根本没写）—— 这时只能靠间接证据，且**必须声明证据不足**
- 被测对象**本身是非确定性的**（如真实网络 / 并发调度）—— 只能靠重复采样

### 需要人工裁决

- 两种口径都"说得通"时取哪个（**这是业务判断**，不是技术判断）
- "数字差多少算噪声"（取决于量纲与用途）

## 一句话

> **数字不对先怀疑尺子：换工具、换口径、换层，最后让断言在修复前自己红一次。**

---

> 本技能的价值全在"承认自己的数字可能是假的"——藏起来的假数字会让后面每一步都建在沙子上。


把**无关信号**算进阈值，指标就会持续误报或漏报。

- 反例：用"孤立括号行数 = 0"当验收，把中文全角 `）` 因排版折行单独成行也算了进去 ⇒ 永远不为 0，
  于是反复判定"没修好"，去改本来正确的代码。
- 正确做法：让指标**只对目标形态敏感**（例如"矩阵里的数字是否还出现在文本层"——
  数字消失 = 已渲染成图；这类指标既正向、又不可伪造）。
- 自检：给指标喂一个**已知合格**样本和一个**已知不合格**样本，两者必须给出相反结论。
  只对"不合格"有反应、对"合格"也报警的指标，是坏指标。

## 原则 8：前置条件缺失 = 假通过

一个"全绿"的结果，可能只是因为**你根本没测到目标路径**。

- 反例：渲染开关由 `config` 决定（默认关闭），测试脚本没传 `config` ⇒ 整份输出走"纯文字回退" ⇒
  图数 = 0 却判定通过；第二次补上 `config` 才发现真实情况完全不同。
- 正确做法：测完**核对"目标侧确实被触发了"**（图数 > 0、日志里出现该分支、计数器非零）。
- 通用句式：**"这个通过的测试，能证明它真的执行了被测代码吗？"** 答不上来 ⇒ 结果不算数。

## 原则 9：只查一个方向的差量断言（单向断言）

凡是 `delta = now - t`、`a - b` 这类差量比较，只断言**一侧**，就等于把另一半交给运气。

- 反例：新鲜度检查只写 `age_days = (now - updated_at) / 86400 > 30 ⇒ 过期`。
  有人把 `updated_at` 手写成 **31 分钟后的未来时间**，`age_days` 变成负数，`> 30` 永远为假
  ⇒ 这条检查对任何"手写未来时间"的文件**永久通过**。不是偶尔失灵，是"愿意就能关掉"。
- 正确做法：**双边断言** —— 太旧要红，太新也要红。容忍度只用来吸收时钟抖动（本例 ±10 分钟），
  并且**写死在代码里**，不做成可配置项（可配置就等于留了一个开关）。
- 自检句式：**"喂它一个未来值 / 上限外的值，它会红吗？"** 不会红 ⇒ 它就是单向断言。
- 推广：不止时间。分数（只查 ≥60、不查上限溢出的 120）、计数（只查非零、不查重复计数）、
  哈希（只比前缀、不比全串）都是同款写法。**任何比较都要问：上下界都断言了吗。**
- **更根本的一层**：这次的真正根因不是"断言少写了一个方向"，而是**输入源由人手填**。
  人能随手填的字段没有测量价值。所以正确修法是两步 ——
  加双边断言（拦住错误输入），**且**把输入源改成机器生成（`datetime.now()`，不给手动参数）。
  只做第一步，等于给一个本不该存在的输入加了个检查。
- 本技能对应的真实产物：`tools/check_handoff.py` 第 8 条断言（`exit 8`）
  + `tools/bump_handoff.py`（`updated_at` 只许机器生成）。
