# SKILL：何时该回滚 / 不改

> ⚠️ 使用前提：**如实报告失败**（见 `你项目的**状态文档** 项目规范 §诚实报告失误）。

**适用症状**

- 改到一半发现**不对**，但**不想认**（沉没成本："都改这么多了"）
- 调研完在"改 / 不改"之间**摇摆**（两种说法都像有道理）
- 在**同一个架构上补丁越打越多**（第 3 个、第 4 个补丁开始互相打架）
- 实测结果**与预期相反**（方案的前提被推翻）
- 半成品已经动过**用户的数据 / 文件**，不知道该不该撤

**不适用**

- 改动**还没落地**（只在脑内/草稿）⇒ 直接改方案即可，不存在"回滚"
- 已经**修复完成且验证通过** ⇒ 那是"正常收尾"，不是回滚场景

---

## 快速判断（30 秒）

```
1. 门禁红了吗？
       ├─ 红了 ──▶ 这个半成品会让"已发布的效果"退化吗？
       │              ├─ 会 ──▶ 【回滚】
       │              └─ 不会 ─▶ 修到绿（但设一个次数上限）
       └─ 绿 ───▶ 2
2. 调研是否证明"不改更优"？
       ├─ 是 ──▶ 【不改】：留档理由 + 当时数字 + 触发条件
       └─ 否 ──▶ 3
3. 在**同一个架构**上，这是第几个补丁？
       ├─ ≥ 4 ──▶ 【停下】：回到架构层（重写 或 回滚）
       └─ ≤ 3 ──▶ 继续（但每次补丁后都要重跑门禁）
4. 实测结果与方案前提**相反**？
       └─ 是 ──▶ 【撤销】该改动，并把"反了的实测"写成结论
```

**判据一句话**：**门禁红 + 会退步 ⇒ 回滚；调研证明不改更优 ⇒ 留档不改；同一架构补丁过三 ⇒ 停下。**

---

## 五条判据（展开）

### 判据 1：门禁红 **且** 半成品会退化已发布效果 ⇒ 回滚

重点在**"已发布效果"**：仓库里已经能用、用户已经在依赖的行为。
半成品即使"新功能是对的"，只要它**让旧行为变差**，就不能留在树上。

### 判据 2：调研后"不改更优" ⇒ 记录理由，不改

"不改"是一个**需要产出物的决定**，不是"什么都不做"。必须留三样：

1. **不改的理由**（为什么改会更差）
2. **当时的数字**（将来有人再提，直接拿数字回复）
3. **触发条件**（什么情况下**应该**重新考虑）

### 判据 3：在错误架构上叠补丁 > 3 次 ⇒ 停下

补丁是**局部修正**；当第 4 个补丁要"绕过前 3 个补丁的产物"时，说明**架构错了**。
此时继续补的代价是超线性的（每个新补丁都要考虑前面所有补丁的相互作用）。

### 判据 4：实测与方案前提相反 ⇒ 撤销，并记录"反了的实测"

前提被推翻时，"修一修再用"通常是错的方向——因为方案的**理由**已经不存在了。

### 判据 5：动过用户数据 / 文件 ⇒ 先保全，再撤，撤完**逐字节复核**

撤文件不是"删掉新文件"那么简单：要**放回备份**并**核对字节**，
否则"看起来回来了"其实已经不一样了。

> **删除前的回滚能力（回收站）见
> `change-verification-with-evidence` §删除也是一种改动** ——
> 撤销一个"删除"动作，前提是**当初的删除本身可恢复**：用户数据与未追踪产出必须走回收站，
> 否则回滚清单上根本没有可执行的步骤（git 救不回未追踪文件）。

## 回滚操作清单（可执行）

```
1. 【保全】把现场的损坏/半成品状态冻结一份（复制，不是移动）
2. 【备份】待撤的文件/数据 → 带日期的备份目录（copy）
3. 【撤】用 git 回滚（代码）或 os.replace 放回备份（数据/产物）
4. 【复核】逐项核对，不能只看"看起来回来了"：
       · 代码：git status 干净 + 文件行数/字节数与原版一致
       · 产物：页数 / 图数 / 字节数（本项目实测口径：1 页 / 13 图 / 229504 字节）
5. 【记录】把"为什么撤"写进文档或 commit 消息（否则下次会重走一遍）
6. 【重跑门禁】回滚后必须再跑一次 --selftest / --smoke（撤的过程本身可能出错）
```

**回滚不等于"白干"**：判据 5 那几次的经验都被写成了设计稿/截图/状态文档 ——
**方案不成立**本身就是最有价值的知识（它省掉了后面所有人的一次尝试）。

## 反模式

### ❌ 半成品"留着反正没坏"

半成品会**退化已发布效果**（用户看到的是"以前好的现在不好了"）。
它也不会自己变好，只会让下一个人以为"这是有意的设计"。

### ❌ 回滚不记录

下次还会有人提同样的方案、走同样的弯路。**"为什么不成立"必须写下来。**

### ❌ "不改"不写理由

"不改"如果没有理由，就会被当成"没做"而反复重提。
（对照：本项目每次"不改"都带**当时的数字** + **触发条件**。）

### ❌ 在错误架构上打第 4 个补丁

第 4 个补丁的复杂度不是加法的，是**乘法**的（要考虑前三个的相互作用）。
到这一步应该**回架构层**：要么重写、要么回滚重来。

### ❌ 回滚后不验证

撤的过程本身可能出错（文件没覆盖全、`os.replace` 目标不对、备份本身已坏）。
**必须逐字节 / 逐项复核**，并重跑门禁。

### ❌ 把"来不及"当"不用回滚"的理由

时间压力是**当时的处境**，不是**质量判据**。
门禁红 + 会退步时，"先留着"的代价会在验收/线上加倍返还。

### ❌ 验收打回后回到"实现"而不是"侦察"

验收打回往往意味着**前提错了**，而不是"实现有小 bug"。
直接改实现 = 在没搞清症状的情况下动手。

## 边界

### 能判（客观）

- 门禁是否红（退出码）
- 是否退化已发布效果（对照产物 / 断言）
- 补丁次数（可数）
- 是否动过用户数据（可查）

### 不能判（主观）

- "更优"有时是**观感**判断 ⇒ 需要数字或 A/B 图来支撑，否则只能交人裁决
- **两个方案都说得通**时取哪个 ⇒ 通常是"改动更小 / 更不易退化"的那个

## 一句话

> **门禁红 + 会退步 ⇒ 立刻回滚；调研证明不改更优 ⇒ 留档不改；同一架构补丁过三 ⇒ 停下重想。**

---

> 回滚是需要**主动承认"这条路不对"**的动作——藏起来的半成品会一直退化已发布效果。


判据 3 说"同一架构上补丁 > 3 次就停下"。但真正难的是识别**"我改错了层"**，而不是数补丁个数。
出现下列任一信号，说明问题**不在你正在改的这一层**：

1. **换到第 3 种同类写法还没成**（3 个正则 / 3 个包裹位置 / 3 个 if 分支）——同一层内的表达变化已经用完了，
   继续换写法的期望收益趋零。
2. **补丁必须靠"保护性前置"才能不崩**（加白名单、加哨兵、加"遇到 X 就跳过"）——
   你的补丁在对抗下游的既有契约，而不是在满足它。
3. **修完指标反而更差**（残留从 2 涨到 8、通过率下降）——立刻回退，**不要叠加**。

停下来之后做一件事：**写出这条链路的阶段契约**（输入是什么、谁在哪个阶段做切分/转换、输出形态是什么），
把"我以为它在 A 层"换成"实测它在 B 层"。层找对了，通常只需要一处改动。

## 幂等性自检（文本/结构变换的必检项）

任何"替换 / 包裹 / 转义 / 规范化"变换，先问一句：**同一份输入跑两遍，结果会不会变？**

- 会变 ⇒ 你的变换**不幂等**，迟早二次包裹（`$$…$$` 外层再套一层、转义符翻倍）。
- 判据：`f(f(x)) == f(x)`，且要在**真实语料**上验证，不是构造样例。
- 实现要点：不要用"本行有没有标记"判断是否已处理，要用**跨行状态**（累计的开关/深度/括号配对）。
