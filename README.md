# 我被 AI 糊弄了三个月，然后给它写了 10 份规矩

说个开头。

我本来只是想用 AI 帮我写个桌宠。养在桌面上的小玩意儿，能聊天、能发呆、偶尔说句莫名其妙的话。预期很低，能跑就行。

结果我发现自己大部分时间不是在写功能，是在干这几件事：

1. 验证它说"改好了"的东西到底改没改；
2. 追问它"测试通过"是怎么测的；
3. 收拾它顺手弄坏的、而它自己压根不知道的三处地方；
4. 上下文压缩之后，重新解释一遍二十分钟前我们自己刚定下的方案。

最离谱的一次，它告诉我某个文件"已创建"。我 `ls` 了一下，没有。它说"可能是缓存导致的"。我让它再创建一次，这次有了。然后我发现它上一次创建在了另一个盘符下——它自己也没意识到。

还有一次，它说"测试全绿了"。我问怎么测的。它说跑了一遍。我让它再跑一遍，红了。

这事儿干了一个月之后我想明白了：**它不是故意骗我，是它真的分不清"我以为我做了"和"我做了"。**

于是我换了个思路——不再指望它自觉，开始给它立规矩。

---

## 先记仇，再立法

我干的第一件事是开个文档记仇。每次它翻车，我记一笔：什么情况、它当时说了什么、实际发生了什么。

记到第三十条左右，规律出来了。翻车就那么几类：

- 执行的时候自己把自己骗了（文件没写成、命令没输出、编译过了没跑）；
- 说完成了但没有证据，或者证据是它自己的一句话；
- 改 A 崩 B，因为它动的是共用的底层；
- 上下文一满就失忆，或者换个会话从零开始；
- 同一个坑踩第三次。

于是这 10 份文件，基本是一类坑一份。不是设计出来的，是攒出来的。

---

## 三条偷懒的经验

### 一、别跟它讲道理，写下来

我试过在对话里说"你要仔细一点"，没用。第二天换个会话，它还是那样。

不是它不听话，是**它每次开工时看到的上下文就那么多**。你在这一轮说的话，下一轮就不在了。

所以正确做法是：把要求写到它每次都一定会读到的地方。

我用两层：

- **`AGENTS.md`** —— 放全局，每次会话自动加载。里面只写"绝对不许干什么"，一条一句，二十来条，读完三秒钟。它不写具体怎么做。
- **`skills/`** —— 具体怎么做，按需加载。

为什么非得分开？因为 `AGENTS.md` 是**每次全量塞进去的**。你往里面塞技能细节，它就会涨到几千字，然后 AI 开始忽略它——不是叛逆，是**重点被稀释了**。

反过来，只有二十条硬规矩的时候，它是真会被执行的。就这么现实。

### 二、它一定会忘，别跟这个较劲

上下文窗口一定会满，压缩一定会发生，会话一定会断。这跟毅力没关系，是物理限制。

所以别设计"它应该记得"的方案，设计"它忘了也能五秒接上"的方案。

就三个 md：

- `HANDOFF.md`：最新进度，永远一屏，开工第一个动作就是读它；
- `ARCHIVE.md`：全部历史，**只许往后面追加，绝不许整个读**；
- `ARCHIVE_INDEX.md`：历史目录，先查索引找到"第几卷、哪个锚点"，再只 grep 那一小块。

关键在**禁止整读**。我早期的失败全在这儿——文件本身没问题，是"让 AI 通读一遍历史"这个动作把自己撑死了。80KB 的归档喂进去，它连当前任务都记不住了。

### 三、让它提意见，但笔攥在自己手里

同一个坑踩第三次，如果每次都要我重新教一遍，那这套东西就是死的。

所以我让它自己发现"这个坑我踩第三次了"，自己起草一条新规矩。但——

**它没有写盘权限。** 草案只在对话里打印出来，我看完说"可以"，才真正写进文件。

为什么卡这一道？因为我试过让它写完。它理解偏了，写进去，然后接下来所有会话都按错的执行，而且我压根没发现。**自动写盘等于让它给自己的错误立法。**

这道人工审批不是为了防它偷懒，是防它自信。

## 十个文件，分别治什么病

按我踩到的频率排的。

1. **`agent-execution-hygiene`** —— 如果你见过它说"文件已创建"而实际没有，或者命令跑完屏幕一片空白它说"成功了"，就看这个。九条规矩，核心就三句：写完先确认文件在，没输出算失败，编译过了不算跑过了。

2. **`change-verification-with-evidence`** —— 如果你问"你确定吗"它答"我测试通过了"，再问"怎么测的"它开始打太极，看这个。它逼 AI 交四段证据：改之前是坏的、改之后是好的、别的功能没坏、提交之后再跑一遍还是好的。少一段都不算完。里面还有两条我特别爱用的：比内容指纹别比总数；删东西必须能从回收站拿回来。

3. **`when-measurement-lies`** —— 如果你改的代码看着完全没错，数字就是不动；或者某个断言永远通过、通过得有点可疑，看这个。它列了六种测量骗人的方式。最常见的一种是：前置条件根本没到位，测试压根没跑，所以永远绿。

4. **`when-to-rollback-or-not-change`** —— 如果你已经在同一个地方改到第三版，而且每版都比上一版多一层 if，看这个。一句话：同一处第三个补丁修不好，说明你改错层了，该往回退，不是往前加。里面还有个自检，做文本替换的人最好背下来——`f(f(x)) == f(x)`，跑两遍结果不一样就说明有鬼。

5. **`recurring-root-cause-atlas`** —— 如果你修好的 bug 过两天从另一个地方冒出来，看这个。AI 最擅长就地消掉眼前这个报错，最不擅长顺着根看还有几处同款。处理办法就一句：修完一处，全仓搜同款。

6. **`source-code-recovery-from-pyc`** —— 这个希望你一辈子用不上。文件被写坏了，git 里没有干净版本，只剩 `__pycache__` 里那点东西。里面讲怎么从 `.pyc` 把源码捞回来，捞回来怎么逐段验证。

7. **`windows-path-damage-diagnosis`** —— 如果你昨天还好好能用的命令，今天突然"不是内部或外部命令"，看这个。我踩过一次：装完某个软件，PATH 被写坏了，`D:\Program Files\` 变成了 `D:\Pro;ram Files\` ——分号插在单词中间。里面写了怎么从注册表时间戳证明"什么时候坏的"，再从系统日志找"谁干的"，全部只读，别一边修一边毁证据。

8. **`session-handoff`** —— 就是上面那三个 md 文件的具体写法，什么时候写、为什么不许整读归档、归档怎么分卷。

9. **`skill-evolution`** —— 如果你第三次对它说同一句话，看这个。它规定了什么时候该把这句话升级成规则，怎么判断是"改旧的"还是"新建一个"，以及为什么写盘前必须你点头。

10. **`workflow-template-1`** —— 如果任务有点大，你怕它跳步直接说完成了，看这个。八个节点：侦察、报告、决策、实施、验证、门禁、提交、验收。重点它不是流水线，是带返工环的——验证不过就退回实施，验收不过就退回决策。

## 怎么装

每个技能是一个目录，里面一个 `SKILL.md`：

```
~/.dsh/skills/
├── agent-execution-hygiene/SKILL.md
├── session-handoff/SKILL.md
└── ...
```

`~` 在 Windows 上是 `C:\Users\你的名字`。

**没有任何依赖。** 纯 Markdown，不用装包、不用编译、不用跑脚本。复制过去就能用。

每个 `SKILL.md` 开头有一段 frontmatter：

```yaml
---
name: session-handoff
description: Use at the start of any session in a workspace that has HANDOFF.md...
---
```

这个 `description` 不是简介，是**触发词**。AI 靠它判断当前任务要不要加载这个技能。所以写"会话交接"没用，写"当工作区存在 HANDOFF.md 时应加载"才有用。我第一次写的时候全写成了名词，一个都没被加载过。

配上 `AGENTS.md` 一起用：

```
~/.dsh/AGENTS.md     ← 二十来条硬规矩，每次自动注入
~/.dsh/skills/       ← 具体技能，按需加载
```

`AGENTS.md` 里每条末尾挂一个"详见 skill: xxx"，让它知道往哪儿翻。仓库里的 `AGENTS.repo.md` 是我自己那份，可以拿去当模板，但建议你先把里面的内容删掉，换成你自己的坑——抄别人的规矩你是执行不下去的。

**如果你用的不是 DSH**，而是 Claude Code / Cursor 之类支持规则目录的工具，把目录换成对应的约定（比如 `.claude/skills/`），`SKILL.md` 格式基本通用。

## 第一次用，别全装

我一开始把十个全塞进去，结果是它一个都不看。

建议按这个顺序：

1. 先只放 `agent-execution-hygiene` 和 `change-verification-with-evidence`。这两个直接治"假完成"，见效最快。
2. 写一份自己的 `AGENTS.md`，从你最近三次翻车里抄出三条"绝对不许"。**别抄我的二十条**，抄了也不会执行——只有你自己的事故才记得住。
3. 用一周，看哪类问题还在犯。那就是你下一个要装的。
4. 等上下文第一次撞墙，再上 `session-handoff`。**撞之前就装**，别等它开始胡说八道了才想起来。
5. 等你说出第三遍同一句话，再看 `skill-evolution`，你会立刻明白它为什么存在。

## 它治不了什么

说清楚比吹有用。

**它不能让 AI 变聪明。** 它只能让 AI 吹牛的时候更容易被拆穿，翻车的时候更容易回滚。这两件事的区别很大——前者是智商问题，后者是流程问题，而流程能修。

**它不能代替测试。** 它管的是"你怎么证明你真测了"，不是"测试写得好不好"。测试本身稀烂的话，证据链再完整也没用。

**它不会自动生效。** 这些全是给人读的（严格说是给 AI 读的）文本文件。你不加载，它就不存在。而且就算加载了，AI 也未必每次都遵守——**所以才需要第 2 条那个技能**。

**它不是通用的。** 里面的案例全是我本机踩的：Windows、PowerShell、Python、一条文档生成流水线。思路可以搬，命令基本得自己换。

## 关于案例

里面的路径、报错、日志片段我保留了原样，因为改了就没说服力了——"某项目某文件"这种脱敏过的话，看着就像编的。

但这意味着**里面的路径你一个都不能直接抄**。看到 `D:\Project\某项目\` 这种，那是占位符；看到 `C:\Users\<你的用户名>` 这种，那是要你自己填。

`windows-path-damage-diagnosis` 里有一整段 PATH 被写成 `D:\Pro;ram Files\` 的原始记录，那是我真实的系统变量，故意留着的——这是整个案例的核心证据，改了这段，那份文档就只剩空话了。

## 最后

这些不是设计出来的，是撞出来的。每一份背后都是一次真实的翻车：一次静默的编码事故、一次删掉又找不回来的文件（顺便说，那次我还以为进了回收站，其实被永久删了）、一次改了 A 崩了 B 的重构、一次上下文炸了之后它开始一本正经胡说八道。

写下来就一个目的：**同一种坑，别踩第二次。**

欢迎提 PR，特别是这两类：

- **补新坑**：你踩到了里面没有的，写一份 `SKILL.md` 提上来；
- **纠错**：某条规矩在你那儿不成立，或者干脆是错的。**这类最值钱**，因为它能防止别人照着错的东西执行。

如果这堆东西帮你省下过一次事故，那就够本了。
